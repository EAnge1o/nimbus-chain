# NimbusChain 设计文档

本文解释**为什么这样分层、每个关键决策的取舍是什么、以及哪几处是最容易写错的**。
README 讲"它是什么"，这里讲"它是怎么想出来的"。

---

## 1. 分层与依赖方向

```
crypto ─┬─> merkle ─┐
        ├─> tx ─────┼─> block ─> chain ─┬─> mempool ─┐
secp256k1 ─> script ┘                   ├─> spv      ├─> node ─> cli / server / demo
                                        ├─> notary ──┘
                                        └─> p2p
```

依赖是**严格单向**的：`crypto` 不知道 `tx` 的存在，`script` 不知道 `chain` 的存在。
这条约束带来三个直接好处：

1. **没有循环导入**，每个模块都能单独 import 与单测。
2. **每层都能独立被理解**：读 `script.py` 的人不需要先理解重组。
3. **可替换**：`crypto.sha256` 有纯实现与 `hashlib` 两条后端，脚本从不关心用的是哪条。

为了让 `script` 与 `tx` 解耦，`OP_CHECKSIG` 需要的 sighash 通过一个**注入的回调**
提供（`script.Checker`）：

```python
class Checker:
    def __init__(self, sighash, locktime=0, sequence=0xFFFFFFFF): ...
```

`tx.checker_for(tx, index)` 负责把 `tx.sighash` 绑到闭包里。这样"栈与签名的逻辑"
留在 `script`，"交易序列化的逻辑"留在 `tx`，两边都不必知道对方的内部结构。

## 2. 密码学层

### 2.1 为什么哈希要写两遍

| 后端 | 用途 | 谁在用 |
|---|---|---|
| `sha256_pure` | 一份可逐字节比对的**标准答案** | 测试、教学、审计 |
| `sha256`（默认 `hashlib`） | 挖矿、批量哈希 | 生产路径 |

纯 Python SHA-256 实测比 `hashlib` 慢约 480 倍（见 `benchmarks/bench_crypto.py`）。
因此"全部手写"如果只有纯实现，会让挖矿慢到不可用；如果只有 `hashlib`，又无法证明
实现者理解 SHA-256。**两个都要，并把它们钉死在同一个测试里**，才是正确取舍。

`ripemd160` 相反：**只有纯实现**。原因是 `hashlib.new('ripemd160')` 在部分 OpenSSL
构建里已被移出默认 provider，跨平台不可靠；而它只用于地址生成，不是热点路径。

### 2.2 坐标选择：为什么用 Jacobian

仿射坐标下每做一次点加都要一次模逆。模逆是 `pow(a, -1, p)`，虽然是 C 实现，
仍远贵于几次模乘。Jacobian 坐标 `(X : Y : Z)` 表示仿射点 `(X/Z², Y/Z³)`，
点加/倍点全是乘加，**只在最后转仿射时做一次模逆**。

实测：标量乘约 0.16 ms，验签约 3.12 ms。这个量级足以支撑：
343 个单测在 11 秒内跑完，且一次转账只需一次签名 + 一次验签。

### 2.3 RFC 6979 不是"优化"，是安全需求

ECDSA 的致命失败模式是 **nonce 复用**：同一个 k 签两条不同消息，私钥可以直接解出来
（这是 2010 年索尼 PS3 被攻破的原因）。RFC 6979 用 `HMAC-SHA256` 从
`(私钥, 消息摘要)` 确定性地派生 k，从而**结构上消灭**"随机数不好"这一类事故。

它还带来一个工程上的红利：**签名逐字节可复现**。测试因此可以断言具体的 r、s 值
（我们用 Bitcoin wiki 上公认的 "Satoshi Nakamoto" 向量），而不是只能"验签通过"。

实现上最容易错的两处：

- `bits2int` 在输入长度**超过** `qlen` 时要右移截断，**在恰好 256 位时不能取模**。
- `bits2octets` 才是"对 N 取模"的地方，两者不能混。

### 2.4 low-S 与 DER

- **low-S**：`s > N/2` 时取 `N - s`。数学上 `(r, s)` 与 `(r, N-s)` 等价，但**不归一化
  会让同一笔交易的签名有多种字节表示**，从而让 txid 变得不确定（BIP 62 的动机）。
- **DER**：严格解析。拒绝长度不一致、非最小化整数（`02 02 00 01`）、负数（最高位为 1）、
  尾部多余字节。宽容解析等于给自己开了一个"签名可延展"的口子。

## 3. 脚本层

### 3.1 条件执行的正确语义

最容易写错的地方：**处于未生效分支里的 `IF` 不能弹栈**。

```
OP_0 OP_IF        ← 条件为假，进入「不执行」状态
  OP_1 OP_IF      ← 这里的 OP_1 根本没有被压栈，所以 IF 不能弹
    ...
  OP_ENDIF
OP_ELSE           ← 只翻转栈顶条件
OP_ENDIF
```

我们的实现里，"是否执行"由 `conditions` 列表决定：

```python
def executing() -> bool:
    return all(conditions)
```

- 在执行状态下遇到 `IF/NOTIF`：弹栈顶求值，把结果压入 `conditions`。
- 在**不执行**状态下遇到 `IF/NOTIF`：直接压入 `False`（**不弹栈**），只记录嵌套。
- `ELSE` 翻转栈顶；`ENDIF` 弹出一层。
- 不执行状态下，除条件指令外一律跳过。

`tests/test_script.py::test_nested_if_inside_unexecuted_branch_does_not_pop`
就是钉这条规则的——去掉 `"if not executing(): conditions.append(False)"` 这个分支，
测试立刻因为栈下溢而变红。

### 3.2 CScriptNum

数值编码是**小端 + 符号位 + 最小化**：

| 值 | 编码 | 坑 |
|---|---|---|
| 0 | `""`（空） | 空串是合法数值，不是"没有值" |
| 1 | `01` | |
| 127 | `7f` | |
| 128 | `80 00` | 单字节 `80` 会被读成 **-128** |
| -1 | `81` | |
| -128 | `80 80` | |

否定判定也要小心：**负零**（`0x80`）在脚本里是**假**。`cast_to_bool(b"\x80") is False`。

`CLTV` / `CSV` 需要**按 5 字节解码**：`1 << 31`（sequence 禁用位）用 4 字节放不下
（`80 00 00 00` 会被读成负数），最小化表示必然要 5 字节。

### 3.3 P2SH 的两阶段执行

P2SH 的语义不是"先跑脚本 A 再跑脚本 B"，而是：

1. 执行 `scriptSig`，栈顶是 **redeem script**（序列化后的字节）。
2. 用副本执行 `scriptPubKey`（`OP_HASH160 <hash> OP_EQUAL`），**只校验哈希**。
3. 弹出 redeem script，**以它为 `scriptCode`** 执行它本身——这一步决定最终真值。

第 3 步里 `scriptCode` 必须是 redeem script（而不是 `scriptPubKey`），否则签名会算错。
`verify_input` 里的顺序与副本处理就是这个语义的直接翻译。

### 3.4 多签的 off-by-one

`OP_CHECKMULTISIG` 会**多弹一个元素**——中本聪当年把循环指针写错，留下了一个
"多推一个 dummy" 的约定。这个 bug 已经不可修复（改了就是硬分叉），所以我们的
实现也必须**如实**多弹一个：

```python
_require_stack(stack, 1)
stack.pop()          # 著名的 off-by-one：兼容历史上多推的那个元素
```

签名与公钥都必须**按顺序匹配**（第 i 个签名只能配第 j≥i 个公钥），乱序签名会被拒。

### 3.5 `OP_CHECKSIG` 的栈序

**栈顶是公钥，下面是签名**。写反了会导致"P2PKH 永远验不过"，而且错误信息会
出现在完全无关的地方（`OP_EQUALVERIFY` 失败）。这个 bug 在我们的开发过程中
真实出现过，并被 `test_valid_p2pkh_spend` 抓住。

## 4. 交易与 sighash

### 4.1 legacy sighash 的四步

```
1. 复制整笔交易
2. 把【所有】输入的 scriptSig 清空
3. 只把 index 那个输入的 scriptSig 换成 scriptCode
4. 序列化 + 4 字节小端 hash 类型，再做双 SHA-256
```

第 2 步是**防跨输入重放**的关键：否则把某笔交易的一个输入换成别的输入，
签名依然有效。测试 `test_other_inputs_scripts_are_blanked` 钉住这一点。

第 3 步的 `scriptCode` 取决于花费类型：

| 类型 | scriptCode |
|---|---|
| P2PKH | `scriptPubKey` 本身 |
| P2SH | 弹出的 **redeem script** |
| 裸多签 | `scriptPubKey` 本身 |

`_find_and_delete` 负责在 `scriptCode` 里删掉签名自身的推送（legacy 规则）；
对 P2PKH 与 redeem 脚本，它实际上什么都不删，但对包含签名的脚本是必要的。

### 4.2 为什么只支持 `SIGHASH_ALL`

`SIGHASH_SINGLE` / `SIGHASH_NONE` 会引入"签名的承诺范围"这一层语义，且在
legacy 实现里有一个著名的历史 bug（`SIGHASH_SINGLE` 在 index 越界时返回 1）。
教学项目的正确做法是**明确不支持并抛错**，而不是实现一个自己都说不清范围的版本。

## 5. 共识层（`chain.py`）

### 5.1 校验流水线的顺序是有讲究的

```
父块存在 → 区块非空 → 大小上限 → PoW → bits 一致 → MTP → Merkle 根
        → 无重复交易 → coinbase 位置 → 逐笔 UTXO/签名/成熟度/超发
```

把**便宜的检查放在前面**（PoW 是一次哈希，Merkle 是几十次哈希），把**贵的检查
放在后面**（签名验证是毫秒级）。这样垃圾区块在第一步就被挡掉。

"无重复交易"必须在签名验证之前：重复交易会让 Merkle 根与某个合法区块相同，
是 CVE-2012-2459 那类攻击的温床。

### 5.2 难度重定目标的三个细节

```python
actual = last.timestamp - first.timestamp        # first 在高度 height - interval
actual = clamp(actual, timespan / 4, timespan * 4)
target = prev_target * actual / timespan
target = min(target, pow_limit_target)           # 不能比下限更松
```

1. **窗口边界**：`first` 是 `last` 往回走 `interval - 1` 步得到的（即高度 `height - interval`）。
   差一步就会算错起始点，且只在"恰好跨过边界"时才暴露。
2. **钳制顺序**：先钳制时间跨度，再乘除。反过来会把除零与极端值引进中间步骤。
3. **下限**：`pow_limit` 是**最松**的难度（最大 target）。难度只能更"难"，
   否则一条低算力链可以靠把难度调到最低来自我加速。

**关键工程决策**：这套规则只在 `block.compute_retarget_bits` 里实现**一份**，
全节点（`Chain.expected_bits`）与轻客户端（`SPVClient.expected_bits_at`）都调用它。
各写一份的后果是：某天其中一份改了钳制顺序，链与轻客户端会**静默分叉**——
不报错，只是对同一高度给出不同的 bits，然后谁也接不上谁。
`tests/test_spv.py::test_client_computes_difficulty_independently` 会逐高度比对两者的结果。

### 5.3 重组：为什么按累计工作量而不是高度

```python
work(bits) = 2^256 / (target + 1)
```

`target` 越小时 work 越大，正是"难度越高、工作量越大"。用**累计 work** 而非高度
来选主链，意味着：

> 一条 2 个块、每块难度 4 倍的分支（work 24576）能击败一条 4 个块、
> 每块难度 1 倍的分支（work 20480）。

这就是"51% 攻击需要 51% 算力"的底层原因。若按高度选链，攻击者可以用低难度块
堆出一条很长的"伪主链"。演示脚本第 5 段与 `tests/test_chain.py::ReorgTests`
都真实构造了这个场景。

### 5.4 重组为什么需要 undo 记录

重组 = 断开旧分支 + 连上新分支。断开时必须**精确还原** UTXO 集：

- 把该块**花掉的** UTXO 放回去（连同它们的 `height` / `is_coinbase` 元数据）
- 把该块**创造的** UTXO 删掉

顺序不能反：如果同一个块内后一笔交易花了前一笔的输出，`created` 里就会包含
一个也被 `spent` 记录的 key；先放回再删除，净效果才是"这个块没来过"。

`BlockUndo` 保存的正是这两张表。没有它，只能全量重放（O(链长)）——本项目把
全量重放留着做**验证手段**：

```python
assert chain.utxo == chain.replay_utxo_set()
```

增量集（`_connect` / `_disconnect` 维护）与全量重放（`replay_utxo_set`）**必须永远
一致**。这个断言出现在 6 个测试里，包括重组之后。

### 5.5 被挤出主链的交易去哪了

`_reorganize` 把被断开区块里的**非 coinbase** 交易收集到 `AddBlockResult.reaccepted`，
由调用方（`FullNode`）交给交易池。这个设计把"共识"与"交易池"解耦：
`chain.py` 不认识 mempool（否则会循环导入），它只负责**如实报告**。

漏掉这一步的后果：被重组挤出的交易永远不会再被打包，用户会以为转账"丢了"。

### 5.6 coinbase 唯一性（一个真实踩到的坑）

最初的实现里，同高度、同收款地址的两个竞争区块会产生**完全相同**的 coinbase 交易，
于是：

- 两条分支共享同一个 txid → `_tx_index` 被覆盖 → `confirmations` 给出错误答案
- UTXO 的 key 在两条分支间**撞车** → 重组后账本难以推理

真实矿工靠 extranonce 解决。我们用 `unique_extra_nonce(prev_hash, timestamp, txids)`
派生一个区块唯一的标记，既保证唯一性又可复现。这个 bug 是被
`test_reorg_updates_utxo_and_index` 抓出来的——**测试的价值就在这里**。

## 6. 交易池、钱包与网络

### 6.1 交易池的本质是"预校验 + 排序"

交易池必须先于区块做一遍校验，否则矿工会把注定失败的交易打进块里，白白浪费一个 PoW。
它比区块校验多两件事：

- **依赖**：一笔交易可以花另一笔还在池子里的交易输出（子交易等父交易）。
  入池时记录 `depends`，打包时必须**拓扑序**，且父交易被剔除时子交易一起走。
- **冲突**：同一个 outpoint 只能被池中一笔交易花掉。

排序按 `fee / size`（聪/字节）。矿工的产出是"手续费 / 区块字节"，
所以 1 笔 500 聪 / 1000 字节的交易（0.5 聪/字节）比 1 笔 300 聪 / 200 字节（1.5 聪/字节）
更不值得打包——按绝对手续费排序会得出相反结论。

`refresh()` 的写法值得注意：清空索引后，**按拓扑序重新逐条 add**。
这样"已确认""冲突""悬空"三种失效情况用同一段代码处理，不需要写三套逻辑。

### 6.2 P2P：定位器与孤儿池

**只比高度会漏掉分叉**。两个节点高度都是 1、但链尖不同（同一高度的两个竞争块），
如果握手里只交换高度，"落后就去拉"的判断会得出"谁都不落后"，于是**双方永远
发现不了对方的分支**。

正确做法是 Bitcoin 的 **block locator**：从链尖往回按指数步长取一串哈希
（`tip, tip-1, tip-2, tip-3, tip-5, tip-9, …, genesis`，长度 O(log n)）。
对端找到第一个认识的哈希，从那之后开始发。双方都在握手里发定位器，
于是**彼此的分支都会被发现**（合法的分支先作为侧链保存）。

**孤儿池**解决另一类乱序：如果对端广播了高度 2 的区块而我们连高度 1 都没有，
这个块接不上。直接丢弃的后果是"明明广播了区块，对端却永远停在旧高度"。
我们的处理是：先验 PoW（否则垃圾块能灌满内存）→ 挂进孤儿池 → 主动索取父块 →
父块到位后**递归解开**（支持链式孤儿）。

还有一个更隐蔽的坑：父块可能是以**侧链**形式到达的。如果只在"成为主链尖"时才去
解开孤儿，就会漏掉这种情况。我们的修复是：**只要该块被成功保存（无论是主链还是侧链），
就继续尝试解开挂在其下的孤儿**。

### 6.3 挖矿在事件循环里

PoW 是 CPU 密集的，理想做法是放到独立进程。当前实现直接在 asyncio 事件循环里跑，
代价是每挖一个块（演示难度十几毫秒）P2P 会短暂停顿。选择这个取舍的原因是：
**并发地改同一份 chain 状态引入的数据竞争，比十几毫秒的停顿危险得多**。
生产实现应当把挖矿隔离到子进程，通过消息队列与主进程交换区块。

## 7. 轻客户端

SPV 的安全性来自两件事，**缺一不可**：

1. **区块头的 PoW + 链式链接**：篡改任何头部要重做工作量证明；改一处要改其后所有块。
2. **Merkle 证明**：不需要交易列表，只要 `log2(n)` 个哈希就能证明"某笔交易被
   某个区块头承诺过"。

实现上刻意的"不信任"：

- `bits` **由客户端自己按历史时间戳重算**（调用与全节点同一个
  `compute_retarget_bits`），不采信对端给的难度。
- 时间戳必须大于**本地** MTP。
- 证明必须挂到**本地已校验过的**区块头上。若对端给一个从未验证过的 `block_hash`，
  证明再漂亮也毫无意义——所以 `verify_transaction_inclusion` 会抛 `SPVError`
  而不是返回 `True`。

诚实声明局限：本实现只跟随**单条**头链，不做竞争头链的分叉选择；
也不做 bloom filter。区块头由调用方成批喂进来（真实场景来自 P2P 的 `getblocks`）。

## 8. 存证应用

### 8.1 为什么选"可检测篡改"而不是"防篡改"

区块链**不能**阻止有人改文件。它保证的是：**改完以后再也证明不了这份文件当时存在**。
措辞上必须严格区分——说"防篡改"会在答辩现场被一句话问倒：

> 评委：那我把文件改了，你链上怎么阻止我？
> 你：链上阻止不了，但任何人拿原文件重新算一次摘要，就会发现链上没这个哈希。

### 8.2 链上只放 32 字节

`OP_RETURN` 输出携带 `SHA-256(文件内容)`，**不携带文件本体**。这带来两个好处：
链不会因为存文件而膨胀；文件留在持有者手里，符合"存证"而不是"托管"的定位。
代价是它**不解决文件丢失问题**——这一点在 README 的局限里写明。

### 8.3 验证结果必须分层

`VerificationResult` 把四种状态分开：

| 字段组合 | 含义 |
|---|---|
| `present=False` | 链上根本没有这个摘要（文件被改过，或从未存证） |
| `present=True, confirmed=False` | 交易还在交易池里，尚未上链 |
| `present=True, confirmed=True` | 已确认，`confirmations` 给出深度 |
| `spv_verified=True/False` | 另一个轻客户端能否**独立**证实 |

一个只返回 `True/False` 的接口会把这些关键差别全部抹掉——而"还没上链"和
"没存过"对用户的意义完全不同。

## 9. 已知取舍汇总

| 决策 | 选择 | 代价 | 为什么值得 |
|---|---|---|---|
| 哈希实现 | 纯实现 + `hashlib` 快路径 | 两份代码要维护 | 可交叉验证，且挖矿可用 |
| 曲线坐标 | Jacobian | 代码更复杂 | 少 90% 以上的模逆 |
| sighash 类型 | 只支持 `SIGHASH_ALL` | 不支持的场景直接报错 | 不实现自己说不清范围的语义 |
| 主链选择 | 累计工作量 | 需要维护 work 索引 | 这是"最重链"规则的本质 |
| 重组 | undo 记录 + 全量重放双路径 | 内存与代码量增加 | 两条路径互相印证，杜绝静默不一致 |
| UTXO 校验 | 每次链尖扩展复制一份 dict | O(UTXO 数) 拷贝 | 校验与提交分离，失败不留痕 |
| 持久化 | 可读 JSON | 慢、体积大 | 教学可读性；真实实现应参考 `nimbus-db` 的 WAL |
| P2P 范围 | 定位器 + 孤儿池，无地址簿 | 不能独立组网 | 共识与验证才是重点 |
| 挖矿位置 | 事件循环内 | 短暂阻塞 P2P | 避免并发修改链状态的数据竞争 |
| 应用选题 | 文档存证 | 不处理文件存储 | 演示冲击力强，且与链的本质对齐 |
